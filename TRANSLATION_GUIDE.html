Translation Guide

v3.0 // DOCUMENT CLASSIFICATION: PUBLIC

Since v3.0 you are no longer forking the mod. You translate one file of keys, ship it as a tiny companion mod, and the game's language setting does the rest.

The Model Changed in v3.0

How it works
KDSP v3.0 looks up every display string by a stable key through Codeware's localization system (Codeware is already a KDSP requirement). Strings/English.reds defines all 11,427 keys with their English text. Your translation is a package that defines the same keys in your language.

Creating a Translation

Step 1 — Get the key list

Open r6/scripts/backgroundScanner/Strings/English.reds from the mod. Every line looks like:

this.Text("Kdsp-Job-JOB_LOCAL_FIXER", "Started doing jobs for a local fixer. ");

First argument: the key — never change it. Second argument: the English text — this is what you translate.

Step 2 — Fill in your language's stub file

The mod ships a stub file for every game language in Strings/ — German.reds, Polish.reds, Russian.reds, all empty and already registered in the provider. A translation is that stub, filled in:

  1. Copy Strings/English.reds over your language's stub (e.g. onto Strings/German.reds)
  2. Rename the class from English to the stub's class name (German)
  3. Translate the values — keys stay exactly as they are

That single file IS the translation. Publish it on Nexus as a file users drop into r6/scripts/backgroundScanner/Strings/, replacing the stub.

// Strings/German.reds — replacing the shipped stub
module KiroshiDeepScan.Localization
import Codeware.Localization.*

public class German extends ModLocalizationPackage {
    protected func DefineTexts() -> Void {
        this.Text("Kdsp-Job-JOB_LOCAL_FIXER", "Fing an, Aufträge für einen lokalen Fixer zu erledigen. ");
    }
}
Why not a separate companion mod?
Earlier versions of this guide described a standalone mod with its own ModLocalizationProvider. Community testing (thanks to our German translator) showed that pattern doesn't reliably override the base mod's English fallback — the fallback registration wins the key conflict. The drop-in stub method routes everything through one provider and is confirmed working. Stub class names are stable across updates, so your file keeps working.

Step 3 — Ship it

Publish your filled-in stub file on Nexus. Users install it by dropping it into r6/scripts/backgroundScanner/Strings/, replacing the empty stub. Partial translations are fine — untranslated keys show English.

Step 4 — Test

Set the game language to yours, scan a civilian, a gang member, and a unique NPC (Takemura, Regina). If you see a raw key like Kdsp-Job-S14 on screen, that key has a typo in your package.

A working example ships with the mod

Strings/French.reds is a partial French translation — 259 keys covering the UI section headers, every scanner loading line, and every BOLO notice. Copy its structure rather than working only from the snippet above.

What the French file demonstrates
Partial coverage works. It translates 259 of 11,427 keys; the rest fall back to English and the mod runs normally — publish at any coverage and grow it.

Word order around dynamic values. Kdsp-Bolo-16 ends mid-sentence because the mod appends a year, then a tail string (Kdsp-Bolo-16b). The French version restructures both halves so the year lands where French grammar wants it.

Every language is pre-registered in Strings/LocalizationProvider.reds — you never edit the provider. Your file replaces the stub for your language.

Translation Rules

⚠️ Preserve inside your strings

  • Tokens — %he%, %his%, %him%, %year%, %young_age%, %corp%. The engine substitutes these after your string is retrieved. Position them wherever your grammar needs.
  • Trailing spaces — events chain into sentences. "...local fixer. " ends with a space; yours must too.
  • Dynamic-value halves — strings ending mid-phrase (e.g. "...missing person report #NC-") get a number appended in code. Keep your structure compatible, or rearrange your sentence so the value lands correctly.
  • Glitch codes & glyphs — ERR_NULL_REF, ██████, [CORRUPTED], ⊕. Translate the human-readable fragments around them; the codes themselves stay.
  • Label glue — fragments like "Status: " and " | Arrests: " are keyed. Translate the words, keep the ": " and " | " punctuation pattern.
BOLO prefixes are now translatable
In v2.4 the BOLO: / ALERT: / NOTICE: prefixes had to stay English because the red highlight matched them as text. v3.0 replaced that with an internal flag — translate the prefixes freely, the urgency color works in every language.

⚠️ Reserved terms — keep verbatim inside your strings

Some words inside translatable strings are matched by game logic and must survive translation unchanged, exactly like the %tokens%:

  • ALL-CAPS words that survive inside longer translated strings — a handful of caps tokens (ACTIVE, VIOLENT, CERTAIN, PLATINUM, SILVER, LAPSED, STOLEN FLAG, NUSA) double as internal state and must stay verbatim where they appear inside a longer translated string. Standalone caps display statuses (CLASSIFIED, KNOWN, DISPUTED, BLACKLISTED, ...) ARE in the key list and fully translatable. ALL_CAPS_CODES and lowercase_snake_case identifiers don't appear in the key list at all — they are internal identifiers, not text.
  • Street drug names — glitter, smash, dorph, spike, stim, synth-coke, Black Lace. These are Night City brand names; the coherence system cross-references them between the medical, psych, and criminal sections.
  • Proper nouns matched by detection logic — corp names (Arasaka, Militech, Kiroshi, NetWatch), gang names, implant lines (Mantis, Projectile), Darknet

Translate the sentence around them; leave these words as-is. If your language must transliterate, transliterate identically everywhere — cross-referencing works by exact substring match.

❌ Not in the key list — by design

  • ALL-CAPS machine values — ACTIVE, FLAGGED, CASH ON DELIVERY, classification codes like SLEEPER AGENT. These are diegetic database output and are used internally by generation logic. They stay identical across languages, like error codes.
  • Name pools — Core/Names/ still works the v2 way: edit those files directly if your language needs transliteration. Most teams leave names as-is.
  • The version footer.

❌ Never

  • Don't change key spelling or case — a mismatched key silently falls back to English.
  • Don't invent new keys — the mod only looks up the keys it ships with.
  • Don't add unescaped quotes inside strings — use \".

Migrating a v2.x Translation

Your strings map 1:1 — content didn't change, only the delivery. Open your translated fork's files next to Strings/English.reds, match each English original to its key, paste your translation into your package. Function names became key suffixes (JOB_LOCAL_FIXER → Kdsp-Job-JOB_LOCAL_FIXER), so most mapping is mechanical.

Release Checklist

  • Every key copied verbatim from English.reds (no typos, no case changes)
  • All %tokens% present where the English had them
  • Trailing spaces preserved on sentence-chaining strings
  • Dynamic-value strings end where the appended number belongs in your grammar
  • Glitch codes, NC- formats, and glyphs preserved
  • File compiles without errors (check redscript_rCURRENT.log)
  • Tested in-game: civilian, gang member, unique NPC, with your language selected
  • No raw Kdsp-* keys visible in any scan
  • Mod page lists Codeware and KDSP as requirements
